# PulseQueue

PulseQueue is a testing-only Final Fantasy XIV input plugin with two cooperating
features:

1. a short, exact, one-shot smart buffer for a press that vanilla FFXIV rejects
   only because it arrived slightly before local readiness; and
2. native held-input Turbo for standard hotbars, so holding a binding produces
   regular presses through FFXIV's own input path.

The important rule is simple: the player's newest genuine press wins. If an
older Viper weave is held or briefly buffered and the player presses Recuperate,
Purify, Guard, or another standard-hotbar binding, that newer press immediately
preempts the older PulseQueue intent. A repeat generated by PulseQueue or
delegated to ReAction is never allowed to masquerade as a new player decision.

Version 0.3.4 replaces 0.3.3's manual slot/action/macro replay. The live 0.3.3
sample showed that path was effectively inert and over-gated: most attempts were
blocked by compatibility policy, its manual macro pulses observed no action, and
only two direct pulses were emitted. The new path repeats the logical input that
FFXIV is already scanning and lets the game do the rest.

This is an open testing release, not an official Dalamud plugin.

## How native held-input Turbo works

During FFXIV's standard-hotbar binding scan, PulseQueue observes two native facts
for each logical standard-hotbar `InputId`: whether it is pressed this scan and
whether it is still held. When the configured cadence is due, PulseQueue reports
that same held `InputId` as pressed once.

FFXIV then resolves the binding normally:

```text
same held InputId -> native binding scan -> current hotbar slot
                  -> current action/macro/target -> normal game execution
```

PulseQueue does not manually invoke `ExecuteSlot`, replay a captured action,
parse macro lines, select a target, or choose a fallback skill. This matters for
combo and transforming jobs such as Viper: every press reaches the current slot
state rather than a stale captured action tuple.

It also means a held macro repeats as a complete player-authored native slot.
Single-action, multi-action, and otherwise arbitrary macros follow FFXIV's own
macro executor. All commands and side effects in that macro can run again, so
the player remains responsible for the macro's contents.

Only one logical input owns PulseQueue repeat at a time. A newer physical press
becomes the owner immediately. The older continuously held input stays
suppressed until it is released; it cannot resume later and steal control back.
Missed cadence intervals never cause a catch-up burst.

## Smart-buffer contract

- Vanilla FFXIV always receives the original player press first.
- One captured intent can produce at most one delayed queue-mode action call.
- The action type, requested and adjusted action IDs, target, extra parameter,
  route, and safety context are immutable while that one-shot intent is pending.
- A genuine newer standard-hotbar press immediately cancels the older pending
  intent. If the older press created an exact PulseQueue-owned native queue,
  only that exact unchanged queue may be cleared before the new press runs.
- Injected Turbo presses and ReAction-delegated repeats never preempt, replace,
  or cancel a genuine newer player intent.
- There is no FIFO weave backlog, action priority list, rotation, alternative
  skill selection, automatic target selection, target fallback, or retry after
  server rejection.
- The one-shot lifetime never exceeds 180 ms. Local response measurements may
  shorten the window but cannot extend it.
- Death, stun, forced movement/knockback, mounting, target change, action
  transformation, zoning, logout, job/PvP context change, frame stall, plugin
  disable, and uncertain ownership cancel the pending one-shot intent.
- Foreign, changed, or unproven native queue state is never cleared.
- PulseQueue never writes animation lock, cooldowns, resources, or targets.

The one-shot buffer and held-input Turbo are separate. Turbo improves repeated
input delivery; it does not turn a failed smart-buffer replay into another retry.

## ReAction and NoClippy coexistence

PulseQueue treats ReAction features as capabilities, not as a reason to disable
the whole plugin:

| Other plugin state | PulseQueue behavior |
|---|---|
| ReAction Turbo Hotbars on | ReAction owns the held-input pulse. PulseQueue observes/classifies the pulse and does not inject a duplicate. The separate smart buffer remains available. |
| ReAction Turbo Hotbars off or ReAction absent | PulseQueue supplies native logical-input repeat itself. |
| ReAction Macro Queue on | ReAction owns macro action queueing. PulseQueue does not apply a second conversion. |
| ReAction Macro Queue off or ReAction absent | PulseQueue can optionally place action calls emitted by macros into FFXIV's normal queue mode. |
| NoClippy on | Supported. NoClippy remains the animation-lock correction owner; PulseQueue neither changes nor duplicates that work. |

The optional **Queue actions invoked by macros** setting changes only the native
mode of action calls emitted by the macro. It does not enable macro repetition,
parse the macro, reorder lines, remove waits, select a skill, or change a target.
Native held-input Turbo repeats the whole held macro slot regardless of that
queue-mode setting.

If ReAction is absent or cleanly unloaded, PulseQueue's own logical-input repeat
remains available. An unsupported or unreadable loaded ReAction build is handled
fail-closed: PulseQueue does not add a second cadence or action mutation, while
the native/ReAction input path remains pass-through until the profile is audited.

## Testing scope and limits

Version 0.3.4 native Turbo covers logical inputs scanned for FFXIV's ten standard
hotbars. Initial delay and repeat interval are independently configurable from
0 through 1000 ms; defaults are 0 ms and 60 ms. A zero initial delay still
waits one repeat interval after the original physical press, preventing the
original scan from producing an immediate duplicate. Out-of-combat repeat is a
separate option.

This release does not implement held-input Turbo for:

- cross hotbar or controller input;
- direct mouse clicks on a hotbar slot; or
- calls made directly by another plugin without a held standard-hotbar
  `InputId`.

Those paths remain vanilla. A mouse button assigned as a normal standard-hotbar
binding can still have a logical `InputId`; directly clicking the slot itself
does not.

The native integration is signature-sensitive and remains testing-exclusive.
It must pass the current-patch live matrix before the project can claim complete
in-game validation. The input hook is fail-open: if PulseQueue cannot safely
classify a scan, the original native pressed result is returned.

## Install

After a testing release has been published, add this URL under **Dalamud
Settings -> Experimental -> Custom Plugin Repositories**:

```text
https://raw.githubusercontent.com/kittenhaswares-ui/PulseQueue/main/repo.json
```

Enable testing plugins, install **PulseQueue**, then use `/pulsequeue` to open
its settings and live diagnostics.

Useful commands:

```text
/pulsequeue
/pulsequeue on
/pulsequeue off
/pulsequeue status
/pulsequeue turbo on
/pulsequeue turbo off
/pulsequeue turbo macros on
/pulsequeue turbo macros off
/pulsequeue dry on
/pulsequeue dry off
/pulsequeue log on
/pulsequeue reset
```

The historical `turbo macros` command now controls macro **action queueing**.
It does not decide whether a held macro slot repeats.

## Important account-risk notice

Square Enix prohibits third-party tools and unauthorized gameplay-modifying
software. A bounded design and transparent source can reduce implementation
mistakes, but cannot make plugin use sanctioned, undetectable, or account-safe.
Use is entirely at the user's own risk.

The official Dalamud repository also restricts combat automation and PvP
advantages. PulseQueue is therefore published only as a testing custom-repository
plugin and does not claim eligibility for the official repository.

## Validation and disclosure

The implementation and review were substantially AI-assisted. The repository
publishes source, deterministic tests, build scripts, release fingerprints, and
a mandatory live-test matrix for human audit. Version 0.3.4.0 is not described
as fully in-game validated until the new native path passes that matrix on the
current FFXIV patch.

The design was compared with the exact upstream implementations used by the
test profile: [NoClippy 0.5.0.24 animation-lock handling](https://github.com/UnknownX7/NoClippy/blob/3f4b37739bbdccd1833b042018b01be84a7d382b/Modules/AnimationLock.cs)
and [ReAction 1.3.5.1 Turbo Hotbars](https://github.com/UnknownX7/ReAction/blob/9436e0c72c569b5518c67bda2e29f44822c68ea0/Modules/TurboHotbars.cs).
PulseQueue's implementation is clean-room; no source was copied from either
AGPL project.

See the [architecture](docs/ARCHITECTURE.md), [live-test matrix](docs/LIVE_TEST_MATRIX.md),
[validation report](docs/VALIDATION_REPORT.md), and [changelog](CHANGELOG.md).
